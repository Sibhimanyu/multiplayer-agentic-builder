Many agents. One objective. No mothership.

Flotilla coordinates parallel coding agents that run on your own team’s laptops, on your own subscriptions. Share a session with one command: you draw each person a seat, they run their own Claude or Codex inside it, and an agent that needs more asks you instead of stopping. File scope is locked before work starts, not discovered at merge. GitHub stays the source of truth.

Share a session new

Hand someone a seat, not the whole repo.

One command shares your session and draws the guest’s seat — the files they may change. Each person runs their own Claude or Codex. Outside the seat an agent is refused, so it asks; you answer yes for this ticket, yes for good, or no with a reason. Here it is on something that is not a website: a slide deck, with the second speaker owning slides 5–8.

  1. 01The host draws a seat

    flotilla share gives Priya slides 5–8 and prints one line to send her.

  2. 02She brings her own agent

    flotilla connect, on her laptop, her subscription.

  3. 03Slide 2 is refused

    Her agent finds a typo on slide 2. It is outside her seat, so the lock is refused.

  4. 04So it asks

    flotilla request, or the request_scope tool, with a reason.

  5. 05Granted for this ticket

    flotilla grant. Slide 2 opens for T-14 only, not for good.

  6. 06Shipped, and locked again

    The grant ends with the ticket. Priya never quietly owns slide 2.

  7. 07The agents talk

    flotilla say or send_message. A message never grants anything.

The problem

Two agents editing one repo is not two developers editing one repo.

Agents work faster than review, do not read each other’s minds, and will happily rewrite the same file from two branches at once. The failure is not that any one agent is bad. It is that nothing tells them what somebody else already owns.

01

Silent collisions

Two agents pick tasks that touch functions/items/. Neither is told. You find out at the rebase, after both have finished.

02

No shared truth

The API shape one agent decided on lives in its own head, or on an unmerged branch. The agent waiting for it is blocked and cannot say why.

03

Hosted sandboxes cost money

Renting a container per agent means paying for idle time and handing your code to a third party. Your laptop is already there, already authenticated.

How it works

A shared board, a shared branch, and no agent on the network.

Work does not move by chat. Agents append facts to one ledger and read their own inbox off local disk; that rule is what keeps a long session coherent instead of drowning every agent in everybody else’s status updates. When a person or an agent does need to say something, flotilla say sends a message on its own channel — and a message never changes who may edit what.

The store holds what must be atomic

Exactly one agent wins a task claim. File-scope locks are refused at claim time on glob intersection, so a conflict costs seconds instead of a rebase. Presence expires on its own. None of this needs to survive forever, so none of it is in git.

Git holds what must be reviewable

API contracts, data schemas and decisions are code. They live on a shared branch, one file per fact, so merges are purely additive and versions are new files rather than edits — which means a blocked teammate gets a real diff.

Your agent never holds a credential

The agent reads and writes plain files in .agentic/. The CLI does every network call. Prompt injection cannot exfiltrate a token the agent was never given, and unsent work survives a crash because it is already on disk.

Your compute, your subscription

Every agent runs locally under whoever owns that laptop. Flotilla coordinates; it does not execute. There is nothing to provision per agent and nothing to pay per agent-hour.

The board

Six columns, one per state, and nothing you have to interpret.

The board follows the task state machine exactly. A card carries its kind, its branch, its owner, and any badge that matters — CI failure and blockage are visible without opening anything. Presence is a ring on the avatar, not a separate panel to go read.

Presence you can trust

Green working, red blocked, grey gone. Staleness is derived when you read it, so a dead laptop cannot look healthy.

Honest freshness

The nav tells you how old the data is. It never shows a live indicator over stale data.

Blockage with a chain

A blocked card names what blocks it, all the way down, not just the nearest link.

Contracts in place

The published contract renders inside the card, with its version and what it supersedes.

Roles and seats

A role is a permission, not a paragraph asking nicely.

Every seat gets a generated prompt telling its agent what it owns. That is guidance. The gates are underneath it: a lock request outside the seat’s file scope is refused, and a deploy outside its deploy scope is refused. No agent can merge.

The seats below are the web template. They are not fixed: a project starts from web, deck or blank, and the host draws any other seat with flotilla share --scope … --label ….

The client seat is safe by plumbing, not by policy

A client’s words are human-layer messages, and the human layer is never written to any agent’s inbox. So text typed by the least-trusted seat cannot reach an agent’s context at all. There is no filter to misconfigure, because there is no path. An owner or architect turns a suggestion into a task, or declines it with a recorded reason — and that is the step where a human decides what the agents work on.

What it costs

Nothing to rent, because there is nothing in the middle.

Flotilla has no agent hosting to pay for, no seats to license, and no server in the coordination path that you do not already own. The coordination substrate fits inside a free tier at the scale this is designed for.

Agent compute

Your existing subscription. Claude Code, Codex, or anything that can read a file. Flotilla never launches a model on your behalf.

Code and review

GitHub, as you already use it. Branches, PRs and CI are untouched. Nothing is mirrored into a system you would have to trust.

Coordination

A free-tier backend you own. Presence at ten agents was measured at roughly 1.4% of the daily allowance. Expected spend at this volume is zero.

Get started

Four commands to a live board.

Flotilla installs as one CLI and runs from inside your repo. There is no dashboard to configure before you begin — creating the project is what writes the agent files.

Point the CLI at your backend

flotilla init --project <id> records which coordination project this machine talks to. It needs no credentials — it runs before you sign in.

Sign in

flotilla login serves a sign-in page locally and opens it. Use --anonymous for a disposable identity, or --no-browser on a headless box to get the URL printed instead.

Create the project in your repo

flotilla new <name> --template web|deck|blank connects this repo, writes the template’s seats, and writes AGENTS.md plus the .agentic/ tree your agent reads. flotilla share draws a teammate’s seat and prints the flotilla connect line to send them.

Start the bridge, then start your agent

flotilla start runs the loop: it drains what your agent wrote, delivers what your agent needs, and heartbeats. Then open Claude Code or Codex as you normally would. It reads AGENTS.md and begins.

a session, start to finish

# once per machine
$ flotilla init --project my-flotilla
$ flotilla login
  signed in as sam@example.com

# in the repo you want to build
$ flotilla new "Inventory Tracker" --template web
  created proj_inventory
  wrote AGENTS.md and .agentic/

$ flotilla start
  bridge up. draining outbox, delivering inbox.

$ flotilla share --as frontend --label "Rae"
  send: flotilla connect fl_8f21c4

# your teammate, on their laptop
$ flotilla connect fl_8f21c4
  connected as rae (frontend)
$ flotilla start

# anytime
$ flotilla status
  3 agents live, 1 blocked, 2 open
$ flotilla ls
$ flotilla members proj_inventory

Offline is a normal state, not an error. Your agent keeps working and the CLI publishes when the network comes back.

Availability, stated plainly

Flotilla is pre-release. The CLI is not on npm yet, so today you install it from the repository or from a built tarball rather than with a package manager, and you point it at a coordination project you provision yourself. If you want to run it now, start from the source repository — the setup steps live there and are kept current.

Scope

What Flotilla deliberately is not.

Every line below was a decision, not an omission. Knowing them up front is the fastest way to tell whether this fits how your team works.

It does not host your agents

No sandboxes, no per-agent containers, no code leaving the laptop it was written on. If you want a hosted agent platform, this is the wrong tool and always will be.

It does not merge for you

Agents push branches and open pull requests. They cannot merge. Review stays where your team already does it, with a human deciding what lands.

It is not a chat interface

People and agents can send each other a short message — “I renamed the chart on slide 6” — but a message changes no fence and grants nothing. Work still moves as contracts, locks and state transitions, the things actually worth another agent’s attention.

It is not a multi-tenant SaaS

You run the coordination project. There is no vendor account holding your board, and no plan to put one in the path.

Independent vessels, separately crewed, moving together.

That is the shape of the system, and it is where the name comes from. There is no place the work happens, because every agent is somewhere else.
