How it works

The mechanism, end to end.

Two halves that each hold what the other is bad at: an ephemeral store for anything that must be atomic, and git for anything that must be reviewable. Everything else in this document follows from that split.

Two copy defects worth remembering, because they recurred

The product named a GitHub webhook in on-screen text for weeks after the mechanism became a poll, and three separate renames each covered the binary and missed a surface it prints (generated role packs, an empty state, the env var block in --help). The rule that came out of it: assert the absence of the retired name in every artifact a user can see — built bundle, generated files, --help, and the served tarball — not in the source.

2. Architecture

There is no server in the coordination path that the team does not own, and no agent is reachable from the network. Every agent sits behind NAT on somebody’s laptop, which is why push-to-agent was never an option and why the bridge exists.

Why the bridge holds so much

The Spark plan has no Cloud Functions, so anything that would have been server-side moved into the CLI: the stale-claim reaper, the PR/CI poll, and the privileged writes that firestore.rules refuses from a browser. Blaze plus one function is the documented upgrade path and was deliberately not taken — it would add a bill with no spending cap for work the bridge already does.

Membership is a document, not a custom token claim, and that is on purpose: a claim needs a token refresh to revoke, and revocation has to be immediate.

3. The split, and why it is the whole design

No single system is good at both atomic contention and reviewable history. Each fact goes where it belongs.

FactDurableAtomicNeeds a diffLives in
API contractforevernoyesgit
Data schemaforevernoyesgit
Decision + rationaleforevernoyesgit
Task claimtransientyesnostore
File-scope locktransientyesnostore
Heartbeatsecondsnonostore
Task statemediumnonostore

Moving contracts out of the ledger removed three problems at once: a hard character cap on the durable text column, silent emoji corruption in an append-only log, and the complete absence of any diff between contract v1 and v2 — which is the single most useful thing a blocked consumer has.

4. The ports

Two interfaces, deliberately separate. CoordinationStore is ten operations inside one project. ProjectDirectory is the project tier. They were not merged into one fifteen-operation port because that would put unproven surface behind a proven gate, and force every future backend to implement multi-project before it could implement coordination at all.

CoordinationStore — ten operations

// ledger
appendEvent(project_id, event, idempotency_key)   idempotent on the key; a repeat
                                                 returns the ORIGINAL {event_id, seq}
readEvents(project_id, since_seq, limit?)         ascending by seq; limit caps at 300

// claims — atomic
claimTask(project_id, task_id, agent_id)          exactly one winner; the loser gets
                                                 {ok:false, owner} — a normal outcome
releaseTask(project_id, task_id, agent_id)        idempotent; releasing what you do
                                                 not own is a no-op

// file scope — server-enforced, not advisory
acquireScope(project_id, agent_id, task_id, globs)  rejects on glob intersection with
                                                   a live lock; returns the conflicts
releaseScope(project_id, agent_id)

// presence — must NOT cost a durable row update per call
heartbeat(project_id, agent_id, status, task?, branch?)
listPresence(project_id)

// read + notify
readSnapshot(project_id, etag?)                   returns null when the etag matches
subscribe(project_id, from_seq, onChange)         fires once immediately, then on
                                                 every change; survives network loss

freshness                                        {mode:'live'} or {mode:'poll', stale_ms}

ProjectDirectory — the project tier

createProject · listProjects · getProject
addMember · listMembers · setRole · revokeMember

The CLI creates projects; the browser lists and opens them. Creating a project means connecting a repo, writing .agentic/ and generating role packs — all of which need the repo on disk. So client writes stay denied, nothing in the rules is loosened, and no billing is required.

Rulings that are part of the contract

  • The auth header is X-Agent-Token, never Authorization.
  • created_at is metadata and is never an ordering key. Order by seq.
  • seq is monotonic ascending; gaps are legal. It comes from a dedicated allocator, never from a row id — a live probe showed row ids are allocated from per-shard blocks and run backwards across inserts.
  • Never match on an error message string. Map to typed errors.
  • NotProvisionedError is required and distinct — “this platform cannot do this” is not the same as “this failed”.
  • Read the structured field, never the exit code.
  • Strip emoji and 4-byte UTF-8 from all durable text before write, in every implementation.
  • A third implementation, memory, exists so the conformance suite can run with no cloud at all.

5. Protocol v0.2 — three layers

Every event carries a layer, and the layer decides who receives it. Version 0.1 had eleven activity-shaped event types delivered to everybody; v0.2 replaced them because progress narration is worthless to another agent and costs it context.

Contract layer — agents subscribe. This is the payload that matters.

KindBody
schema_published{ name, path, commit_sha }
contract_published{ name, version, path, commit_sha, supersedes }
contract_superseded{ name, old_version, new_version, breaking, migration_note }
decision_recorded{ path, commit_sha, title, affects_tasks[] }
scope_locked{ agent_id, task_id, globs[] }
scope_released{ agent_id, task_id }
task_unblocked{ task_id, was_blocked_by, reason_resolved }

path + commit_sha point into the git blackboard. Content is never in the event.

Coordination layer — agents subscribe.

KindBody
task_claimed{ task_id, agent_id, role_slug }
task_completed{ task_id, agent_id }
task_blocked{ task_id, reason, blocked_by_task_id }
branch_pushed{ branch, commit, task_id }
pr_opened{ task_id, pr_number, pr_url, branch }
ci_passed / ci_failed{ task_id, pr_number, check_name, details_url }
merged{ task_id, pr_number, commit }

The last five originate outside the agents, with actor_type: 'github'. The design said webhook; the shipped mechanism is the bridge’s poll.

Human layer — dashboard only. Never delivered to an agent.

KindBody
agent_heartbeat{ status, task_id, branch, harness }
task_progress{ task_id, summary, files_changed[] }

This exclusion is normative

An agent subscription that includes the human layer is a protocol violation. It is the single most important rule in the protocol: it is what keeps agents sharp over a long session instead of drowning in each other’s status updates. It is also what makes the client seat structurally safe — a client’s text is human-layer by definition, so it cannot enter any inbox.jsonl. Prompt injection from the least-trusted seat is impossible by plumbing, not policed by a filter.

What agents share, and what they do not

Share — high value, low volume

  • API contract: endpoint, request, response, version
  • Data schema: table, columns, types
  • File-scope lock: who owns which paths
  • Task state transitions: done, blocked
  • A decision plus its rationale
  • A blocking failure that changed the plan

Do not share — low value, high volume

  • Progress narration
  • Agent reasoning or chain of thought
  • Full file contents — git already has them
  • Questions to each other — route to the human
  • Retry and error chatter
  • Heartbeats — infra signal, not semantics

Envelope

{
  "event_id": "evt_01J9X2",
  "project_id": "proj_inventory",
  "seq": 4211,
  "layer": "contract",
  "kind": "contract_published",
  "actor_type": "agent",
  "actor_id": "agent_backend_1",
  "created_at": "2026-08-25T09:41:02.881Z",
  "protocol_version": "0.2",
  "body": {
    "name": "items-api", "version": 2,
    "path": "contracts/items-api.v2.yaml",
    "commit_sha": "a3f9c1e0d4b28f6712c9ab3e5580f1d2c7e46a9b",
    "supersedes": 1
  }
}

Reject an unsupported major version. Accept additive fields within a minor.

Read-your-own-writes

An agent that appends and receives seq = N may immediately read a snapshot reporting seq < N, because publication is debounced. That is stale, not lost. Track last_written_seq locally and treat snapshot.seq < last_written_seq as “not yet folded”. Do not retry the append — retrying here is the most likely source of duplicate events in the whole system.

6. State machines

Task

open ──► claimed ──► in_progress ──┬──► needs_review ──► pr_open ──► merged ──► done
                          │        │
                          └► blocked
                                   └► cancelled
  • open → claimed requires an atomic claim.
  • claimed → in_progress on first local work.
  • in_progress → blocked requires a reason and, where known, blocked_by_task_id.
  • needs_review → pr_open and pr_open → merged come from GitHub, not from an agent’s assertion.
  • merged → done automatic, or owner-confirmed.

The board’s six columns are these states, in this order. That is not a coincidence and it is not open for reinterpretation.

Agent session

connected ──► idle ⇄ claiming ⇄ working ⇄ blocked ⇄ reviewing ──► offline
                                                                  revoked

stale is derived at read time from last_heartbeat_at against a 90 s default. It is never stored — a stored staleness flag is a flag that can be wrong, and the failure mode is a dead laptop that looks healthy.

7. Claims and scope locks

The agent does not claim. It asks.

This was a real gap: the agent had no way to claim anything, because it has no network access by design. The ruling keeps both properties intact.

  1. The agent appends claim_requested to outbox.jsonl.
  2. The bridge calls the verified claimTask — the atomic operation stays where it is proven contended.
  3. The outcome returns on the inbox as a coordination-layer event, win or lose.

A lost claim is a normal reply, not an error. It must not be logged as one, and the CLI exits 0 on it.

Conflict handling

Task claim

Atomic, exactly one winner. The loser receives {ok:false, owner} and picks another task.

File scope

Rejected at claim time on glob intersection with a live lock. The response names the conflicting agent and globs, so the caller can choose differently without asking a human.

Stale claim

The reaper releases claims whose owner has been stale past claim_timeout (default 15 min) and appends task_unblocked. Without it a dead laptop holds a task forever.

Containment is not intersection, and using one for the other is a silent hole

Two different questions with opposite biases. Does this glob conflict with a live lock? is intersection. Is this glob inside the role’s permitted scope? is containment. ** intersects functions/** — so reusing the conflict logic for the permission check would let an agent asking for the whole repo pass a backend check.

Why not read-verify-write

Because it stays racy, and the measured failures are worse than the theory. Against a store with no transactions, a “unique” column did not enforce under concurrent insert — 547 winners for 200 tasks. Its compare-and-set fallback was worse and silent: 658 winners while the durable table looked perfect, so 458 agents held claims they did not own and no database audit could have found them. Both are reportable platform findings, and both are why the claim primitive is verified contended before it is trusted.

8. The .agentic/ file contract

The interface between the CLI and the local agent. The agent speaks filesystem, not HTTP. This is also the answer to “what is the harness launch contract?” — there isn’t one. The contract is a file format, so it works identically for Claude Code, Codex, or a human with echo >> outbox.jsonl.

Layout

AGENTS.md                        generated role prompt, read at session start
.agentic/
  project.json                   { project_id, name, repo_url, brief, protocol_version }
  role.md                        responsibilities, file scope, branch prefix
  protocol.md                    the subset of the protocol the agent needs
  tasks/current-task.md          the claimed task: title, description, acceptance
  contracts/                     materialised from the blackboard, read-only
  decisions/
  inbox.jsonl                    CLI appends. contract + coordination layers ONLY.
  inbox.cursor                   agent writes: byte offset it has consumed
  outbox.jsonl                   agent appends. CLI drains.
  outbox.cursor                  CLI writes: byte offset it has published
  outbox.d/                      spool dir for payloads over 4 KiB
  state.json                     CLI-owned: last_seen_seq, last_written_seq, agent_id

The token lives outside .agentic/, in .flotilla-token at mode 0600, so the agent’s own tree never contains a credential. Add both .agentic/ and .flotilla-token to .gitignore.

What this buys

  • The agent holds no token, so prompt injection cannot exfiltrate a credential it never had.
  • Unsent work survives an agent crash, because it is on disk.
  • Every message the agent tried to send is auditable, byte for byte.
  • Offline is a normal state. Unpublished lines accumulate and the agent keeps working.

Framing rules

JSONL: one object per line, LF-terminated, no embedded raw newlines — escape as \n. A single write() with O_APPEND is atomic in practice under one page, 4 KiB. POSIX does not guarantee non-interleaving above that, and network filesystems break it outright, so: 

# payloads over 4 KiB — and a contract fragment will exceed it — MUST spool
write   .agentic/outbox.d/.tmp-<uuid>
rename  .agentic/outbox.d/<uuid>.json      # rename() on one fs is atomic

A reader never observes a partial file. The CLI drains outbox.jsonl and outbox.d/ together, ordered by mtime.

Cursors, and why the wire path is at-least-once

Separate files, never in-band. The CLI reads outbox.cursor, publishes from that offset to EOF, then writes the new offset after the publish succeeds. A crash therefore re-sends rather than drops — which is exactly why appendEvent requires an idempotency key.

body.local

For contract events the CLI has already fetched the blob and written it to disk, and populates body.local with the path. The agent opens a file. It never makes a network call. A fetch failure appends no line and does not advance lastSeen — announcing a contract whose file is not on disk is worse than announcing it late.

Going the other way, for contract_published the agent names a file it has written into the working tree. The CLI commits it to the blackboard branch, pushes, and rewrites the event body as a pointer before publishing. The agent never deals with commit shas.

9. The git blackboard

One file per fact. Never a shared append-only markdown file.

A single BLACKBOARD.md that every agent appends to conflicts on every merge from every branch, forever. One file per fact makes merges purely additive, so conflicts are structurally impossible. This is the changesets / ADR-directory / migrations pattern. If you take one thing from this section, take this.

The claim was measured rather than assumed: two agents publishing concurrently produced 1 rejection, 1 rebase, both facts landed, nothing lost. 

agentic/blackboard          long-lived, everyone pushes directly, no review gate

contracts/
  items-api.v1.yaml       kept forever, never edited
  items-api.v2.yaml       new version = new file
schema/
  items.sql
decisions/
  0007-qty-is-integer.md

Contracts do not need review to be published — they need review to be merged into main. Pushing straight to a shared branch removes the case where a blocked agent cannot see a contract sitting on somebody’s unmerged feature branch.

Versions are new files, never edits. Editing v1 in place destroys the diff that tells a consumer what broke — and it does so while leaving every path-existence check green, which is why the acceptance test asserts v1 is byte-identical rather than merely present.

Contracts are OpenAPI 3.1 fragments, not prose. A contract that is a paragraph in a text field has moved the ambiguity, not removed it.

10. Roles as capabilities

A role was once a role_slug string plus prose in role.md, which constrained an agent only by asking it nicely. That is not a permission. 

role:
  slug          "backend"
  file_scope    ["functions/**", "schema/**"]     may edit
  deploy_scope  ["functions"]                     may deploy
  capabilities  claim · publish_contract · open_pr

Three enforcement points, deliberately layered — a prompt is guidance, the other two are gates:

The role pack tells the agent its scope

AGENTS.md already does this. Guidance only.

acquireScope refuses globs outside the role’s file_scope

The existing verified primitive, now bounded by role rather than by whatever the agent asks for.

Deploy refuses targets outside deploy_scope

Genuinely new — nothing before this had a concept of a deployable target.

Defaults: owner, architect, backend, frontend, qa, client. The backend-builder / frontend-builder role slugs survive every rename — they are data, not the product name.

The client seat

client can:     read the board · append question and suggestion (human layer)
client cannot:  claim · acquireScope · deploy · publish contracts · run an agent

Triage is a feature, not overhead: an owner or architect turns a suggestion into a task, or declines it with a recorded reason. That step is where a human decides what agents work on, so it is a surface on the board rather than a side channel.

Generated AGENTS.md

# Backend Builder

You own functions, data access, API contracts and backend tests.

## Your file scope
You may edit:      functions/**, schema/**

Generated prose is a product surface, and for a long time nothing tested it

A real agent found the generated pack contradicting itself (“push branches: yes” against “never run git yourself”), claiming contracts were on disk when the directory was empty, and naming a retired command. The assertion — that a freshly generated project contains no stale command name and no claim that is false for an empty project — is the deliverable, not the rename.

Exit codes are deliberate

CodeMeans
0It worked — including a lost claim, and including being offline
1A real failure: bad usage, revoked token, unpublishable state

Diagnostics go to stderr so stdout stays parseable — flotilla status is read by people and by scripts, and interleaving log lines would break both. Unconfigured prints one clean line and the command to run; a stack trace only appears under FLOTILLA_DEBUG=1.

The stranger path

install tarball → flotilla init → flotilla login → flotilla new
   → agent appends claim_requested → bridge claims → card moves
   → agent reports → ledger

Tested under a scrubbed environment with a fresh HOME. That matters: an earlier version of this test passed only because GOOGLE_APPLICATION_CREDENTIALS was still exported, so init found credentials it should never need. A redirected HOME is not a fresh machine. Login cannot be driven headlessly, so that one step is stubbed and says so; everything either side of it is asserted on artifacts — the config file, the project document, the claim document, the ledger event — not on return values.

Quota exhaustion has three different shapes, and “days of runway” fits one

Monthly, depleting, hard wall

Refused, not billed. Every authed route spent 2 SELECTs, so one service’s exhaustion became every service’s outage.

Daily allowance that resets

Cannot be exhausted by this workload. It throttles rather than stops.

Rolling hourly bucket that refills

Exceeding it is a 403 that clears within the hour.

Converting all three into “days of runway” would have manufactured a ratio out of three incompatible mechanisms. Only one route has a depleting budget.

The reading

The routes fail differently, and the choice is which failure you can absorb. Firestore is the only one with a working push subscriber — 191 ms against 5,200 and 8,551 — a primitive verified contended, and a quota that resets rather than walls. The git-only route owns the cost column outright and has the most rigorously verified primitive, but loses every latency row by more than an order of magnitude and cannot meet its own advertised freshness: a 5,000 ms poll is 5,040 requests/hour against a 5,000 limit. Its binding constraint is the dashboard, not the agents — found by that route, against that route.

So: Firestore as the coordination layer, git as the durable store. Close to what the original design proposed, for reasons the design did not know.

Why Flotilla, and what it cost

Drydock named the place work happens. There is no place. The architecture is deliberately local-first: every agent runs on a different person’s laptop, on their own subscription, with no server in the coordination path. A drydock is one fixed location everyone travels to — precisely what this was built not to be. Flotilla names the agents and gets the shape right: many independent vessels, separately crewed, no mothership, moving together toward one objective.

Stated plainly, because it is a real loss: Flotilla says nothing about territory. Ships do not own patches of sea, while Drydock’s assigned zones mapped exactly onto acquireScope and non-intersecting globs — the mechanic that differentiates this product, and the one thing enforced server-side. The runner-up, Mosaic, kept territory and fixed the location problem. It lost on the user’s call.

The rename boundary, both times

Rename the brand, the CLI, the package, the installer, every generated file and every user-facing string. Do not rename the repo, branches, backend project ids, or collections — those are live infrastructure, and renaming them breaks running installs and makes the measured comparison record unreadable.

14. Open items

  • Login is the fragile surface. Four orders went into it: the hosted page used a redirect that ITP breaks, the popup needed a real user gesture, the page had to be served from the CLI, and then the CLI never opened a browser at all — so the user kept landing on the hosted page nobody was fixing. Default now opens the local page and always prints the URL; --no-browser finally does what it says.
  • The CLI is not published. Publishing claims a name on a public registry permanently and is the user’s call. It is publish-ready and verified by installing the tarball into a clean temp directory — packaging that works in the source tree and fails from a tarball is the normal failure, and only the tarball test tells them apart.
  • Artifacts that only exist in git keep going stale. Three separate times: the rules were three weeks behind while hosting deployed repeatedly, the compiled output was behind its source, and the served tarball was built before the command a user tried to run existed. The fix is to build the artifact in the pipeline and assert the downloaded thing against the repo.
  • No Cloud Functions, so no budget exposure — and no server-side authority either. Blaze has no spending cap by default, only alerts, and firebase-tools cannot set a budget. If it is ever enabled, the budget alert is a hard gate a script must not paper over.
  • Nothing is deployed for anyone but this machine. The board is live for the bake-off project only; there is no public instance, and the database region is permanent (asia-south1, chosen so the latency comparison was like-for-like rather than flattered by a US default).
  • An unexplained but localised git wedge. git send-pack wedged while the same host measured 1.9 s in the same minute. Four hypotheses were eliminated by measurement. It is not the adapter — an instrumented replica ran 30 appends flat with zero wedges at the same instant the harness wedged ~3× per append. Mitigated: every git child now gets a deadline and a bounded retry counted in stats.git_timeouts.
  • Two findings worth more than the platform choice, both reportable upstream: a column documented as “enforces unique values” does not enforce under concurrent insert, and compare-and-set reports success to every racer while writing exactly one row. The second is the more serious — a silent violation an audit cannot detect.

Method rules that came out of the work

  • Assert the artifact, not the return value: the installed binary, not npm pack exiting 0.
  • A control that never fires has not been run. A negative assertion is vacuous unless you prove the thing could have appeared.
  • Reasoned is not measured. A figure with no run behind it does not go in the table; the cell says the route owes it.
  • Verify cross-branch invariants by running, not by reading. Two branches reported different test counts from the same command while both looked correct from inside.
  • Report the flake rather than keeping the green re-run. A known-intermittent failure only reported when it blocks something becomes a surprise later.
