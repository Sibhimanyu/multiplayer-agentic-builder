# Product design — Flotilla

> **Historical.** This document framed the product when it was called Catalyst Builder and
> assumed a Zoho Catalyst backend. Both were superseded: decision 0001 chose Firebase for
> coordination with git as the durable store, and decision 0004 named the product Flotilla.
>
> Kept because the **product framing** below still holds — bring-your-own local agent, no hosted
> sandbox, GitHub as the source of truth, coordination through a store rather than agent-to-agent
> messaging. Only the backend it names is wrong. For what is actually built, see the README and
> `docs/designs/project-tier.md`.

## Summary

Catalyst Builder is a lightweight, open-source app builder for teams building Zoho Catalyst apps with humans and local AI agents. It uses Catalyst for coordination, GitHub for code, and each teammate's laptop for actual agent execution.

The product should feel like a multiplayer control room:

> **Status:** architecture superseded 2026-08-25. The coordination design now lives in
> [store-interface.md](../reference/store-interface.md), [protocol v0.2](../protocol/agent-coordination.md),
> [blackboard.md](../reference/blackboard.md) and [dashboard.md](dashboard.md).
> This document is kept for product framing. Where it disagrees with those, they win.
> Corrections applied below: Web Client Hosting is deprecated (use Slate); Signals cannot
> reach a browser or CLI; contracts live in git, not the ledger; polling reads go to Stratus.

1. A user creates a project.
2. The user invites teammates.
3. The user assigns each teammate a role.
4. Each role produces a role pack: skills, task permissions, and an `AGENTS.md` style prompt.
5. Each teammate connects their local `catalyst-builder` CLI.
6. Their local Claude Code, Codex, or other harness builds, tests, pushes branches, and opens PRs.
7. The Catalyst dashboard shows task progress, messages, blockers, branches, PRs, and merge state.

## Product Goals

- Keep hosting cost close to zero.
- Host the coordination layer on Zoho Catalyst itself.
- Keep the project fully open source.
- Avoid hosting per-user agent sandboxes.
- Support local Claude Code and Codex harnesses.
- Use GitHub as the durable code and review source of truth.
- Make the first internal demo useful for Zoho Catalyst app teams.

## Non-Goals for MVP

- Do not clone or fork the full QM architecture.
- Do not host remote coding agents inside Catalyst.
- Do not build a Slack or chat-first interface first.
- Do not build peer-to-peer agent messaging first.
- Do not implement a hosted multi-tenant SaaS control plane.
- Do not let agents merge to main in the first version.

## Why Not QM Directly

QM is a strong reference for org-scoped agent coordination, but it is too heavy for this product's first version. QM includes a central core server, Postgres, auth, admin surfaces, plugins, Slack, durable sandboxes, multiple harness adapters, crons, webhooks, and cloud deployment targets.

Catalyst Builder should borrow these ideas from QM:

- scoped workspaces
- role-owned skills
- durable event history
- admin-controlled permissions
- structured task progress
- local or isolated execution

It should not borrow QM's full operational model for the first version.

## Main User Flow

### Project Owner

1. Creates a project in the Catalyst-hosted dashboard.
2. Connects a GitHub repository.
3. Adds the app brief, constraints, and Catalyst target.
4. Creates or accepts generated tasks.
5. Invites teammates.
6. Assigns each teammate a role.
7. Reviews progress, blockers, branches, and PRs.
8. Merges accepted work through GitHub.

### Teammate

1. Opens the project invite.
2. Accepts role assignment.
3. Runs a connect command locally:

   ```bash
   catalyst-builder connect <invite-code>
   ```

4. Runs:

   ```bash
   catalyst-builder start
   ```

5. The CLI downloads the role pack and writes local context files.
6. The local agent harness claims tasks, edits code, reports progress, pushes branches, and opens PRs.

### Local Agent

The local agent never needs privileged access to the Catalyst dashboard internals. It reads local files generated by `catalyst-builder`, such as:

```text
AGENTS.md
.agentic/project.json
.agentic/role.md
.agentic/tasks/current-task.md
.agentic/protocol.md
```

The bridge CLI handles the network protocol. The agent operates through normal local file and Git workflows.

## Role Packs

A role pack is the contract between the dashboard and a local agent.

Example:

```yaml
role_id: backend-builder
display_name: Backend Builder
skills:
  - catalyst-functions
  - catalyst-datastore
  - api-contracts
permissions:
  can_claim:
    - backend
    - api
    - data
  can_push_branches: true
  can_open_prs: true
  can_merge: false
prompt_files:
  - AGENTS.md
  - .agentic/role.md
branch_prefix: agent/backend
```

Generated prompt:

```markdown
# Backend Builder

You are responsible for Catalyst Functions, Data Store integration, API contracts, and backend tests.

Do not modify frontend files unless the task explicitly says so.
Push work to `agent/backend/<task-slug>`.
Report progress after each meaningful change.
Open a PR when the task is ready for review.
```

## Coordination Model

Agents communicate through a shared project ledger, not direct messages.

```text
Agent A -> Catalyst event log -> Agent B
Agent B -> GitHub PR update -> Catalyst event log -> Agent A
```

Every important action becomes an event:

- `task_claimed`
- `task_progress`
- `task_blocked`
- `task_ready_for_review`
- `branch_pushed`
- `pr_opened`
- `pr_updated`
- `ci_passed`
- `ci_failed`
- `review_requested`
- `merged`
- `agent_heartbeat`

Superseded by protocol v0.2, which splits these into contract, coordination and human layers
and excludes the human layer from agent inboxes. Contract events carry a git pointer, never a
payload. See [Agent coordination protocol](../protocol/agent-coordination.md).

## First MVP

The first MVP should prove one vertical slice:

1. Create a project in the dashboard.
2. Invite two agents or teammates.
3. Assign frontend and backend roles.
4. Each teammate connects the local CLI.
5. Each CLI claims one task.
6. Each CLI writes progress events.
7. At least one branch is pushed to GitHub.
8. A GitHub webhook updates Catalyst.
9. The dashboard shows live-enough progress.

Poll the Stratus snapshot every 5 seconds, adaptive backoff to 30 s when idle. Do not poll
Data Store: a SELECT costs 150x a CDN read and the free tier is 10,000 per month against the
CDN's 300,000. Do not plan on Signals as a later push upgrade - its targets are Webhook,
Function and Circuit only, so it can never reach a browser or a laptop behind NAT.

## Demo App

Use a simple Catalyst app as the first demo target:

```text
Inventory Tracker
  Frontend: item list, add item form, item detail
  Backend: CRUD functions
  Data: items table
  QA: smoke test create/list/update/delete
```

This is concrete enough to split into frontend, backend, and QA roles without needing a complex domain.

## Risks

- GitHub auth could slow the demo. Use each user's existing local `gh` auth for v1.
- Catalyst API specifics verified 2026-08-25 against the installed skill references. Findings
  are folded into [impl-catalyst.md](../handoff/impl-catalyst.md). The one open item is whether
  `is_unique` works on a `varchar` column; probe it before building.
- Local harness launch differs across Claude Code, Codex, and other tools. Start by writing files and letting the user run their harness manually, then automate launch later.
- Agents can conflict if they edit the same files. Use task ownership, branch prefixes, and file-scope guidance in the role pack.
- Polling can feel slow. It is still the right v1 trade-off because it is cheap and debuggable.

## Success Criteria

- A user can create a project from the dashboard.
- A teammate can connect a local CLI with an invite code.
- The CLI can fetch role/task context and write an `AGENTS.md`.
- The CLI can claim a task and report progress.
- The dashboard shows agent status and task state.
- A pushed branch or opened PR in GitHub updates the dashboard through a Catalyst webhook.
- No hosted agent sandbox is required.
